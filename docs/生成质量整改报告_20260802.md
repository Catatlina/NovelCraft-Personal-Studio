# NovelCraft Personal Studio 生成质量整改报告

日期：2026-08-02
审计基线：`origin/main` `0a3261d`（2026-08-02 11:01）
专项范围：上下章节连贯性、长篇事实一致性、情节推进、去 AI 味、质量评分与质量门禁
结论等级：**生成质量为当前最高优先级；整改代码与目标回归可用，真实长篇和人工质量尚未达到验收标准。**

## 一、用户问题与审计结论

用户反馈是：上下章节之间不连贯，去 AI 味效果仍差。代码和现有记录支持这一判断，不能用“50 章跑通”或“AI 腔违例 0”反驳：

- `docs/QA_50chap_report.md` 记录 50 章、205,913 字、综合均值 84.4，但“连贯性”均值只有 84.1，五段趋势从 85.6 降到 80.9，最低章为 70 分。
- 同一报告发现真相在第 40 章前提前揭示 4 次（第 12、22、24、37 章），能力使用却省略代价 13 章；这已经是实质性的跨章因果和约束连续性问题。
- 报告中的“AI 腔违例 0”只代表固定禁词/规则没有命中，不代表经过人工盲评后没有 AI 味，也不代表句式、叙述声音、信息组织和情绪推进像真人作者。
- 当前代码有连续性检查，但检查失败时会放行；事实核对调用有记录但没有把结果应用到正文；V7 的质量评分门槛只有 70，重写门槛只有 60。

最终判定：**当前生成链路可以产出文本，但不能保证相邻章节自然承接，也不能把“去 AI 味”当成完成的人文化改写。**

## 三、生成质量根因

本节记录的是本轮整改前的根因证据；整改后的代码状态、已关闭项和仍需真实验收的项见本章“本轮整改已落地的质量闭环”和第五、六节。

### Q-01：上下文取到了，但没有以“可执行的连续性契约”传给下一章（P0）

#### V7 路径

- `backend/app/v7/generation/generation_engine.py:72-81` 将人物、世界、情节状态的读取上限提高到 120/100。
- 但同文件 `:169-182` 的 `fmt_state()` 只渲染 `items[:20]`，大量已读取状态根本没有进入 Prompt。
- `:89-100` 只取最近 3 章的 `summary`，上一章正文只取最后 400 字；如果摘要为空，前两章不会形成有效前情。
- `:145-151` 对最终上下文直接按字符截断，可能从中间切断设定、事实或约束，且没有按字段优先级保持完整块。
- `GenerationEngine._build_generation_prompt()` 主要要求“与前情和设定一致”，没有强制输入/输出上一章的 `end_state → 本章 start_state`、未解决目标、人物位置/关系/认知变化和时间锚点。

#### V6/V3 路径

- `backend/app/services/assembler.py:127-143` 的 `recent_chapters` 只取最近 3 章摘要；没有稳定注入上一章结尾原文和下一章承接点。
- `:192-199` 的伏笔查询只按 `status='planted'` 和创建时间取前 5 条，没有按“本章应回收/继续推进”筛选。
- `:145-190` 实体状态只取有限条目；关键人物、地点、能力代价可能被最新更新时间挤出上下文。
- `:201-225` 知识召回主要用书名、创意和题材查询，不是围绕当前章节的冲突、人物和待解决事实检索，相关性不足。

这解释了为什么“上下文窗口 30→120”的修复没有完全解决用户感受到的断层：**扩大了数据库读取范围，不等于增加了下一章真正可用、可核对的连续性信息。**

### Q-02：连续性检查是可选且失败放行，不能作为质量门（P0）

- `backend/app/services/chapter_loop.py:530-572` 的语义连贯检查在异常时返回空的高危问题列表；注释明确“never raises”，这会让检查失败看起来像“没有问题”。
- `:734-748` 的连续性守卫只有在配置了 `banned/rules/facts` 时才运行，默认小说未必启用。
- `:806-810` 只有词法检查通过才执行语义检查；语义检查失败不会阻断交付。
- `:968-974` 调用 `write_fact_reconcile` 后只记录 step，没有读取它的冲突结果、修复建议或 replacements，因此“事实核对”可能只是日志存在，并未改变正文。
- V7 `StoryDirector` 调用 `ReviewEngine` 时，`backend/app/v7/engines/review_engine.py:154-175` 的审查 Prompt 主要收到当前正文、有限人物/情节状态和约束，没有上一章尾部、章节转场契约、待回收伏笔和本章预期终态。

因此当前链路是“生成后询问模型这章好不好”，不是“拿上一章的事实和转场要求逐条核对，并在失败后实际修正”。

### Q-03：质量门槛与用户要求不匹配（P0）

- `backend/app/v7/director/story_director.py:43-45`：总分 70 即可标记通过，只有低于 60 才触发重写。
- `:566-575` 目前只对 `constraint_compliance < 80` 做维度级拦截；连贯性、人物声音、写作质量、情绪和节奏没有同等硬门禁。
- `:577-611` 最多只自动重做一次，重做后不保证连贯性维度达标。
- `backend/app/v7/engines/review_engine.py:110-115` 仍以 70 作为审查计划阈值。

这会出现“总分过 70，但相邻章节跳跃、人物声音漂移、文字明显有 AI 味，仍被标记 completed”的情况。对小说生成来说，这个门槛只能证明“模型返回了可读文本”，不能证明“读者愿意继续追读”。

### Q-04：去 AI 味管线名义上七层，实际能力不足（P0）

#### V7

`backend/app/v7/generation/generation_engine.py:343-409` 的 `DeAIPipeline` 只做固定规则处理；`411-543` 主要是套话替换、标点归一、重复压缩、同一代词句式合并、长段落拆分和章末总结删除，没有真实的语义级人文化重写，也没有结合用户文风样本。

其中 `parallel_structure_break` 还会对符合模式的三句文本进行机械合并；它可能减少模板感，但不等于生成了更自然的叙述声音，存在改变节奏和语义重音的风险。

#### V6/V3

`backend/app/services/deai_pipeline.py:121-146`（整改前）实际流程是：

1. 固定词表启发式清洗；
2. 一次 `deai.rewrite` AI 重写，且输入被限制为前 6000 字；
3. 强制拆分过长段落。

文件虽然定义了七层名称，但实际没有七次独立的语义处理。更严重的是 `:141-142` 捕获 Provider 异常后回退到启发式结果，这会让用户收到“处理完成”的文本，但真正的人文化重写没有发生。

#### 本轮接入状态

`backend/app/prompt_registry.py` 的 `final_humanize` 现在由 V7 `GenerationEngine` 和 V6 `chapter_loop` 都通过真实 provider 调用，并做长度/段落保留校验；V6/V7 的上层仍分别使用 sync/async 适配，但 Provider transport、执行账本和 V7 Prompt provenance 已收敛到共享边界，真实 migration/回放仍待补证据。

### Q-05：去 AI 味评分不是可靠的人类感知指标（P1）

`backend/app/services/deai_pipeline.py:38-64` 的 `quick_deai_score` 主要依据固定套话命中数、平均句长、逗号比例、感叹号和连接词评分；它无法判断：

- 叙述声音是否像同一个作者；
- 对话是否有真实的停顿、打断和潜台词；
- 情绪是否通过动作和选择落地，而非抽象心理总结；
- 段落是否只是“换了同义词”，整体结构仍然是模型腔；
- 去味后是否损伤了人物、事实和因果。

所以“AI 腔 0”只能改名为“固定规则未命中”，不能作为生成质量验收证据。

### Q-06：作者风格已接入 V7，但仍缺编辑反馈闭环（P1）

V6 `assembler.py:265-290` 的作者风格卡现在由 V7 `ContextAssembler` 按 project scope 读取并注入生成上下文；但用户保留/删除/喜欢表达尚未形成反馈闭环，仍需真实样本验证其对人感和稳定性的改善。

### Q-07：50 章长跑证明了可运行，不证明质量回归有效（P1）

当前长跑记录只有一组生成结果和模型自评分，缺少：

- 相邻章节盲评前后对照；
- 固定人物/时间线/地点/能力代价事实集的逐条验收；
- 人工编辑对“连贯性”和“AI 味”的独立评分；
- 去 AI 味前后不得损伤剧情事实的差分检查；
- 多个随机种子或不同题材的复测。

现有 17 个通过测试主要验证函数、契约和测试替身协议，不能替代真实长篇质量验收；本轮质量专项中 7 个长篇/真库测试还因注册接口 503 未完成。

## 四、整改方案

### 本轮整改已落地的质量闭环

本轮不是只调整 Prompt，而是把质量结果接入生成状态和 V6 事实源：

- `backend/app/v7/integration/quality.py` 将总分和关键维度门槛统一为 85 分；`consistency`、`character_voice`、`plot_logic`、`writing_quality`、`constraint_compliance` 任一不足即不能通过，最多两次重写，耗尽后标记 `needs_review`。
- `backend/app/v7/integration/v6_bridge.py` 新增 `transition_contract`，保存上一章尾部、上一章交接契约、本章结束状态、事件、开放线程、禁止改变的约束和下一章桥接句；只有通过质量门禁才写入 V6 `contents`。
- V7 上下文不再把完整 Prompt 从头部盲切，而是优先保留交接契约、上一章结尾、约束和前情；Review 同时接收上一章尾部和交接契约。
- V7 `DeAIPipeline` 在规则预处理后调用真实 provider 的 `bootstrap.final_humanize` 语义定稿，并校验长度与段落保留；provider 失败或破坏性缩短会显式失败，不再回退成“处理完成”。
- V6 `DeaiPipeline` 去除 provider 异常后回退到启发式成功的逻辑，并不再把输入硬截断为前 6000 字；章节主链在局部/事实/重规划修复后接入真实 `final_humanize`，并做二次结构化复核。
- `write_fact_reconcile` 增加精确 anchor/replacement 修复契约；V6 主链会实际应用局部修复、二次审查并记录 repair version，修复不通过仍标记 `needs_review`。
- V6 去 AI 重写与 V6/V7 最终人文化均接收作者风格卡/事实约束，Prompt 版本已随模板变更递增。
- V7 读取并注入 V6 `style_cards.author_card/genre_card`；风格卡只约束表达，不覆盖剧情事实。

本轮代码级证据：新增合并质量测试、V6 质量契约和 V7 预算网关回归；共享运行时/Provenance/账本目标组合为 67 passed、2 warnings，全量后端为 843 passed、138 skipped、1 xpassed、2 warnings。真实 provider 多章复测和人工盲评尚未完成，因此本节只能标记为“整改代码已实现/可用”，不能标记为“生成质量已验收”。

### 阶段 A：先建立连续性事实账本

每章定稿必须持久化结构化 `chapter_transition_contract`，至少包含：

- `start_state`：本章开始时人物位置、身体/能力状态、时间、关系、已知信息；
- `end_state`：本章结束后的同一组状态；
- `events_added`：本章发生的事件及因果结果；
- `open_threads`：未解决目标、悬念和伏笔；
- `due_threads`：本章必须推进或回收的事项；
- `forbidden_changes`：不得在下一章凭空改变的事实；
- `next_chapter_bridge`：上一章结尾到下一章开场的具体动作/空间/情绪承接。

下一章生成前先读取这份账本和上一章真实结尾，再生成章节；生成后逐条核对。账本缺失、解析失败或冲突未解决时，状态必须是 `needs_review`，不能当作成功。

### 阶段 B：修正上下文装配

1. 修复 V7 的“取 120、只渲染 20”问题；采用按重要性和当前章节相关性检索，保证关键状态进入 Prompt。
2. 禁止对完整字符串盲切；按“事实块/人物块/转场块/伏笔块/文风块”分块预算，块内不得截断。
3. 默认注入上一章结尾原文、上一章 `end_state`、本章 `start_state` 和本章目标，不再依赖用户手动打开 continuity 配置。
4. 伏笔按目标章节和状态筛选，实体状态按本章相关人物/地点/能力优先，不再简单取最新 10 条。
5. V6 与 V7 共用同一套章节事实账本和转场 schema，避免两套上下文系统各自摘要。

### 阶段 C：把连续性检查改成真正的闭环

1. 连续性检查失败必须 fail-closed：返回 `unverified/needs_review`，不能返回 clean。
2. `write_fact_reconcile` 必须返回结构化冲突、事实修正和可应用的局部替换；调用方必须实际应用并二次审查。
3. Review Prompt 必须同时携带当前正文、上一章尾部、转场契约、事实账本、待回收伏笔和本章细纲。
4. 复审必须检查“新正文相对旧正文没有引入新冲突”，而不是只检查本章自身分数。
5. 重大连贯性问题不允许交付 `completed`；达到重试上限后转人工待审，不能带着“仍有违例”继续自动连载。

### 阶段 D：重做去 AI 味，不再依赖固定词表

建议统一为一条真实 Provider 质量链：

```text
AI 痕迹检测（结构/句式/叙述声音）
  → 标注具体段落和问题类型
  → 局部最小修改（不改事实和剧情）
  → final_humanize 全文人文化定稿
  → 事实/连贯性/长度/风格回归
  → 只接受质量不下降的候选
```

具体要求：

- `final_humanize` 真正接入最终定稿，而不是只保留 Prompt。
- Provider 失败时返回失败/待处理，不回退为“已完成的启发式去味”。
- 去 AI 味输入不能只取前 6000 字；长章按段落块处理，并保留全章事实上下文。
- Prompt 不只写“更自然”，要绑定作者风格卡：平均句长、对话比例、喜欢/不喜欢表达、叙述距离、禁用套话和已确认示例。
- 去味候选必须做剧情事实差分；任何人物关系、时间、地点、能力代价、伏笔状态变化都不得被人文化处理改掉。
- `quick_deai_score` 只能作为预筛指标，不能作为最终“去 AI 味通过”依据。

### 阶段 E：重建质量验收

在重新宣称生成质量可用前，必须完成同一题材、同一创作圣经下的双轨对照：旧链路 vs 整改链路。

最低验收建议：

| 指标 | 建议门槛 |
|---|---:|
| 高危跨章事实冲突 | 0 |
| 上一章结尾承接失败 | 0 个自动通过，失败必须待审 |
| 真相/能力代价/伏笔提前或遗漏 | 0 个高危；中危必须有修复记录 |
| 连贯性维度 | 每章 ≥85，不能只看平均值 |
| 写作质量/人物声音 | 每章 ≥85 |
| 连续 20 章末段相对首段下降 | 不超过 2 分 |
| 去 AI 味盲评 | 至少两名编辑盲评，整改版优于旧版 |
| 去味事实保持 | 100% 通过 |
| Provider/审查失败 | 不得伪装为通过或完成 |

验收样本必须保留每章的输入上下文、事实账本、原稿、去味稿、审查结果、修复记录和最终状态，不能只保留均值图表。
