## 三、问题清单

以下 R-01 至 R-09 保留的是快进到 `0a3261d` 时的审计证据，作为整改前基线；本轮实施后的状态以第四节和最终“不能宣称完成”清单为准。

### R-01：V7 API 缺少认证与资源归属校验（P0）

证据：

- `backend/app/main.py:119` 仅挂载 `/api/v7` 路由。
- `backend/app/v7/api/brain.py`、`director.py`、`trace.py`、`cost.py`、`prompt.py` 的路由主要依赖 `get_async_db`，没有 `get_current_user` 或 `require_novel_member`。
- V6 已有 `backend/app/core/security.py:get_current_user` 与 `backend/app/core/authz.py:147-158:require_novel_member`，但 V7 未使用。
- V7 的 `NovelScopedMixin` 只保存 `novel_id`，没有用户、项目或成员关系约束；V7 API 也没有确认该 `novel_id` 属于当前用户。

影响：只要构造出其他 novel UUID，攻击者可能读取或写入 Brain 状态、目标、约束、版本、决策、事件、Trace、成本数据；Prompt 版本接口还存在全局未授权访问风险。这是项目权限模型未闭合，不是单纯页面问题。

整改要求：

- 所有 V7 路由统一接入当前用户依赖。
- 所有以 `novel_id` 为作用域的读写统一调用 `require_novel_member`，写操作按角色限制。
- 明确定义 V7 novel 与 V6 project/contents 的归属映射，禁止只凭 UUID 访问。
- Prompt 全局管理接口增加管理员/项目范围权限。

验收条件：两个不同用户分别访问同一组 V7 URL；非成员读写均返回 403，成员只能访问所属 novel，审计日志能记录用户身份。

### R-02：DecisionLog 保留 demo 数据与失败伪成功（P0）

证据：`frontend/src/v7/pages/DecisionLog.tsx:51-101` 在 API 失败时填充 `dec-1` 至 `dec-4` 的硬编码数据，并明确写有 `Mock data for demo`；`107-130` 在 approve/reject API 失败时仍在本地修改状态为 approved/rejected。

影响：后端不可用、权限失败或网络错误会被用户误认为已有真实决策和成功审批，违反“失败即失败、禁止伪数据”的交付要求。该问题也与 `docs/V7_AGENT_PAGES.md` 声称“无 mock”相矛盾。

整改要求：

- 删除 demo fallback。
- API 失败只显示错误态和重试入口，不修改业务状态。
- 审批成功必须以后端成功响应为准，并重新拉取或以服务端返回对象更新。
- 增加“API 失败不产生假数据/假成功”的前端测试。

验收条件：断开 API 或返回 401/500 时，页面无 demo 决策、无成功 toast、状态不变化；真实 2xx 响应后才显示更新。

### R-03：CostMonitor 前后端数据契约不一致（P0）

证据：

- `backend/app/v7/cost/cost_manager.py:225-253` 返回 `total_limit_cny`、`total_spent_cny`、`total_remaining_cny` 等字段。
- `frontend/src/v7/pages/CostMonitor.tsx:161-218` 使用 `summary.total_budget_cny.toFixed(2)`。
- 后端摘要没有 `total_budget_cny`，因此真实摘要进入该渲染路径时，首个预算卡片可能直接触发 `undefined.toFixed`。
- 最新生产 walkthrough 主要检查标题和旧 mock 值是否消失，未验证真实摘要字段、页面错误和预算卡片渲染。

整改要求：

- 统一字段命名，推荐以 `total_limit_cny` 为服务端规范，或在 API schema 层明确映射并生成类型。
- 前端对空预算、空摘要和异常响应做显式处理，禁止直接对可能为空的值调用方法。
- 增加真实响应 fixture 的页面渲染测试，并在 Playwright 中断言预算金额、剩余金额及无 console/page error。

验收条件：有预算、无预算、超预算、API 失败四种状态均能渲染；浏览器无运行时异常；金额与 API 响应一致。

### R-04：GenerationConsole 进度字段与后端响应不匹配（P1）

证据：`frontend/src/v7/pages/GenerationConsole.tsx:63-70` 读取 `step_names`、`run_duration_sec`；`backend/app/v7/director/story_director.py:311-332` 返回 `steps_executed`，运行时长位于 `run_stats.duration_seconds`，没有前端所读的两个字段。

影响：生成成功后步骤状态可能全部保持 pending，进度仍显示 0/7，用户看到的是与真实执行不符的进度。

整改要求：确定唯一响应 schema；前后端共享类型或通过 Pydantic/OpenAPI 生成类型；以 `steps_executed` 与 `run_stats.duration_seconds` 驱动页面，并覆盖失败/中断/部分完成状态。

### R-05：成本预算与 Prompt 版本没有接入实际生成（P1）

证据：

- `backend/app/v7/cost/cost_manager.py` 提供预算检查和记账方法，但生成路径没有调用 `assert_within_budget` 或 `record_cost`。
- `backend/app/v7/generation/generation_engine.py:814-845` 直接硬编码 Prompt 名称与版本 `1.0.0`，只将使用信息写入 Trace/run 统计。
- `CostBudgetManager`、`PromptVersionManager` 的调用检索结果主要停留在模块/API 内部，没有实际生成调用链。

影响：预算为 0 仍可能发起 LLM 请求；真实花费不会自动进入预算账本；UI 的 Prompt 版本管理无法证明生成时实际使用了哪个激活版本。

整改要求：将预算检查放到每次 LLM 调用之前，将 token/cost 记账放到成功或失败收口处；生成前解析 active prompt version，生成后写入 prompt execution 记录与 trace provenance；补充超预算阻断、失败不重复记账、Prompt 版本可追溯测试。

### R-06：AI 真值门禁失败，且规则与 V7 架构不一致（P1）

证据：`bash scripts/ai_development_gate.sh` 失败。`scripts/verify_ai_truthfulness.py` 主要识别直接函数调用，而 V7 使用 `AIGateway.generate/generate_json` 等对象方法；同时规则也会将确定性读函数和未被调用的 adapter 标记为风险。

判定：这不能直接证明所有被标记函数都是假 AI，但它证明强制门禁目前不能通过，项目没有形成可持续的“真 AI 调用可验证”规则。

整改要求：扩展 AST/调用图规则识别 V7 Gateway，区分“真实 provider 调用、AI wrapper、纯确定性函数、未使用 adapter”；保留对硬编码结果和 demo fallback 的阻断；新增一条端到端证据链：请求 → provider 调用 → model/provider → token/cost → trace。

### R-07：V6/V7 数据链未闭合（P1，详见合并报告）

证据：`backend/app/v7/db.py:5-8` 明确 V7 与 V6 分离；`backend/alembic/versions/v7_001_init_all_tables.py` 创建独立 `v7_*` 表；`backend/app/v7/director/story_director.py:666-712` 只更新 `v7_story_states`，`719-753` 也只从 Brain state 读取，没有写入 V6 `contents`。

影响：V7 生成的章节不会自动进入 V6 书库、编辑器和导出路径。当前只是入口层和 API 层接入，不是业务数据合并。

### R-08：测试统计与文档基线不一致（P1）

证据：

- `docs/TEST_SUMMARY_20260802.md` 宣称后端 180 passed，但当前可复核的 V7 125 + 编辑器/修复回归 38 并不等于该文档表格中的 180；同一文档还同时出现“编辑器相关 53 passed”和“42 passed”的不同口径。
- 该文档底部称本地与生产版本一致为 `720f40b`，但代码基线已经有 `0a3261d`；应区分“源码 HEAD”和“已部署 HEAD”。
- `docs/QA_GATE_v7_report.md` 仍保留 D1/D2 未修复、Sprint3 未覆盖等旧结论；`docs/V7_AGENT_PAGES.md` 仍描述已被 `720f40b` 清理的多个 mock 页面。
- `docs/AI_HANDOFF.md` 的 V7 状态仍停留在更早提交，且历史段落与当前结论混杂。

整改要求：每份报告写明 commit、测试命令、环境和 skip 原因；统一通过 CI 产出机器可读汇总；将旧审计标注为历史版本或更新为当前结论。

### R-09：版本号生成存在并发竞争（P2）

证据：`backend/app/v7/repositories/version.py:55-96` 采用 `MAX(version_number)+1` 后再插入；迁移中没有 `(novel_id, branch_name, version_number)` 唯一约束。并发请求可能计算出相同的下一版本号。

整改要求：增加数据库唯一约束，并用事务重试或数据库序列/锁保证版本分配；补充并发创建测试。
