# NovelCraft Personal Studio — V3 融合需求与开发文档

> 版本：Draft v1.0
> 基线来源：PRD v2.2、37任务分解、24任务列表、V2全量文档、PRODUCT.md（用户提供）+ V3升级目标说明
> 仓库：https://github.com/Catatlina/NovelCraft-Personal-Studio（未能直接读取代码，本文档基于用户提供的PRD/架构描述整理，落地前需与实际代码对照校准）
> 目的：把 V3 目标架构**嵌入**现有系统，而不是另起一套；明确每个新增能力挂在哪个现有模块上、改哪张表、加哪个节点

## 0. 使用说明（给开发团队）

本文档不是"重新设计一个系统"，而是**在现有 8 个已知子系统上做增量**：

- 创作入口层（扫榜/灵感/拆书）
- Workflow Engine（4节点类型、幂等、断点续跑）
- Agent 系统（10个，禁止互调）
- Context Engine（7层上下文装配）
- Story Bible（人物/世界观/大纲/细纲）
- Quality Engine（七维审核）
- Version System（VersionedRepository、版本树）
- Knowledge Hub（pgvector、风格学习、RAG）

**每一条新增需求都必须先回答三个问题，再排期**：
1. 挂在现有哪个 Agent / 哪个 Workflow 节点上？
2. 改动现有哪张表 / 新增哪个 entity_type？是否要走 VersionedRepository？
3. 是否需要新的 Schema 注册（Pydantic）？是否影响 7 层上下文装配的 Token 预算？

不回答清楚就不允许开发，避免重复 PRD 里说的"假完成/空页面/未接入AI流程"。

## 2. V3 目标架构落点对照表

V3文档提出的8层新架构，实际上不是新架构，是给现有系统的每一层**加字段/加节点/加一层校验**。对照如下：

| V3 层 | 落在现有哪里 | 改动性质 |
|---|---|---|
| 创作入口层 | 现有双入口（扫榜/灵感） | 不变 |
| 创作分析层 | 十层分析 Agent（Trend/Producer） | 输出层扩展：加"创作决策报告" |
| 小说规划层（DNA/总纲/分卷/Arc） | plan_idea + 分层长篇规划（FR-C2-06） | 结构扩展：Novel DNA 实体化 + Arc 实体化 |
| 小说知识层（人物/世界/时间线/关系/伏笔/事件） | Story Bible + C6 一致性引擎 | 字段扩展：认知分层、时间线锚点 |
| 创作智能层（Strategy/Skill/Prompt） | 无对应物，**真正新增** | 新模块，见第6章 |
| 内容生产层 | Writer Agent + 章节生成 | 流程扩展：加 Chapter Function 前置 |
| 质量控制层 | Reviewer + 七维评分 | 扩展：加读者体验维度 + Repair Engine |
| 学习反馈层 | Knowledge Hub 风格学习 | 扩展：Author Style Card 强化 |

## 3. Novel DNA（挂载点：书库 + plan_idea）

### 3.1 数据模型

不新建独立表，作为 `novel` 实体的**结构化元数据**存储（与现有"创作圣经"合并，不是并列关系）：

```
novel_dna (挂载于 novel.meta，走 Pydantic Schema 注册表校验)
├── commercial_positioning   # 商业定位：平台/读者画像/核心爽点/核心卖点/阅读期待
├── story_promise            # 故事承诺：一句话回答"读者为什么追"
└── forbidden_deviations     # 禁止偏离：结构化列表，如"禁止圣母/禁止无理由暴富"
```

### 3.2 流程接入点

- 生成时机：`plan_idea` 节点产出创作圣经的**同时**产出 Novel DNA（同一次 LLM 调用扩展输出字段，不加调用次数）
- 校验时机：`audit_plan_fidelity`（忠实度审计）时一并校验 DNA 内部是否自洽（如"卖点=AI+重生+创业"但"禁止偏离"里写了"禁止穿越"要标记矛盾）
- 硬约束注入：每次 Writer Agent 生成前，`forbidden_deviations` 强制注入写作上下文（复用现有"实体状态表硬约束注入"的机制，不是新写一套注入逻辑）
- 违反检测：并入 Reviewer 七维评分的"设定冲突"维度，不新增独立检测器

### 3.3 工作量与依赖

- 无新表，Schema 扩展 + Prompt 模板扩展
- 依赖：`human_confirm_title` 环节可增加"DNA确认"，但不阻塞现有确认流程（建议合并为一步，避免用户多一次等待）

## 4. 规划层级扩展：新增 Arc（挂载点：分层长篇规划）

### 4.1 现状

现有分层规划已经是：核心玩法→世界观→长主线→阶段路线→**故事弧**→虚拟分卷→卷纲→连续章纲。"故事弧"概念已存在，但目前是**隐式**的（存在于规划流程的产出文本里，没有独立实体、没有状态字段）。

### 4.2 V3 要求 vs 建议落地范围

V3原文要求六层：`卷→阶段→Arc→事件→章节→场景`。

**建议本阶段只做一层**：把"故事弧"从隐式流程产出**实体化**为独立数据对象，不同时加"阶段"和"场景"两层。理由：内容树 `parent_id` 结构和7层上下文装配的 Token 预算一次改两层以上，改造量和回归测试量都会明显放大，而现有系统还有大量 🧪 待验收项，优先级上不划算。"阶段"和"场景"放到 Arc 验证有效之后（第二/三阶段）再加。

### 4.3 Arc 实体设计

```
story_arc (新 entity_type，走 VersionedRepository)
├── novel_id / volume_id      # 归属
├── name                       # 名称，如"第一次创业"
├── goal                       # 目标
├── start_state / end_state    # 开始状态 / 结束状态
├── participants                # 参与人物（关联 character entity_id 列表）
├── core_conflict               # 核心冲突
├── key_events                  # 关键事件（自由文本，暂不拆独立 event 实体）
├── payoff_points                # 爽点
├── foreshadowing_refs            # 关联伏笔（关联现有伏笔系统 FR-C6-04）
├── outcome_impact                # 结果影响
├── status                        # planning / active / completed
└── chapter_range                 # 覆盖章节范围（起止 chapter_id）
```

### 4.4 接入点

- 内容树：`volume` 下新增 `arc` 作为 `chapter` 的可选父级（`parent_id` 支持 arc，向后兼容——没有 Arc 的旧小说 chapter 仍可直接挂 volume）
- 7层上下文装配：在"本卷摘要"和"近3章摘要"之间插入"本 Arc 摘要"一层，Token 预算按优先级重新分配（Arc摘要优先级高于近3章摘要，低于实体状态表）
- 防崩策略：每10章巡检时增加"Arc 进度校验"（当前章节是否偏离 Arc 的 start_state→end_state 轨迹）
- Reviewer：七维评分新增关联 Arc 的偏移检测（复用现有"人物弧线阶段目标校验"的实现模式，Arc 校验和人物弧线校验是同构问题）

## 5. Chapter Function（挂载点：章节细纲）

### 5.1 问题

现有章节细纲缺"本章功能"这一前置约束字段，导致"有事件但无作用"的水字问题。

### 5.2 落地方式（低成本高收益，建议第一阶段直接做）

给章节细纲 Schema 加三个必填字段，生成前置校验（不通过则打回重新细纲，不进入正文生成）：

```
chapter_function (章节细纲新增字段，非独立表)
├── function_type   # 枚举：开篇吸引/信息展示/人物成长/关系推进/冲突升级/
                     #      爽点释放/伏笔埋设/伏笔回收/转折/高潮
├── chapter_goal     # 本章目标，如"父亲开始认可主角"
└── reader_expectation  # 读者期待，如"想知道主角如何赚钱"
```

- 校验时机：细纲生成后、正文生成前，加一个轻量 branch 节点判断三个字段是否为空
- 审核关联：Reviewer 七维评分中"节奏检测"维度读取 `function_type` 序列，检测是否连续多章功能重复（如连续5章都是"信息展示"）判定为节奏问题

## 6. 网文策略库 + Prompt Compiler（真正新增模块，工作量最大）

### 6.1 定位

这是 V3 里唯一**没有对应现有模块**的新增系统，其余都是扩展。必须新建，但**不要一次做成通用引擎**。

### 6.2 分层设计

```
Strategy（经验层，人工整理，非AI生成）
  ↓ 组合
Skill（能力层，可复用的生成函数）
  ↓ 编译
Prompt（最终注入 Writer Agent 的提示词）
```

### 6.3 落地范围建议（第一阶段）

只做 **3-5 个高频策略**验证组合逻辑，不要一上来做成通用 Compiler：

- 优先做：打脸策略、黄金三章、身份反转（爽点类，命中率最高）
- Strategy 数据结构：

```
strategy (新表，非 versioned，人工维护为主)
├── category        # 开篇/爽点/冲突/感情/高潮
├── name             # 如"打脸策略"
├── stages            # 结构化阶段序列：压制→误解→隐藏实力→事件触发→能力展示→群体态度变化→新的目标
└── applicable_conditions  # 适用条件（如需要"隐藏实力"人物设定存在）
```

- Skill 层：先只做和现有 Writer Agent 已有能力对应的（`generate_conflict`、`generate_hook`），不要现在就做 `repair_character`（依赖第7章 Repair Engine 还没建）

### 6.4 Prompt Compiler

不做成独立服务，做成 Writer Agent 生成前的一个**组装函数**，输入现有已有的各层信息，输出最终 Prompt：

```
compile_prompt(
    system_rules,        # 现有
    platform_rules,      # 现有
    genre_rules,         # 现有
    novel_dna,           # 第3章新增
    strategy,            # 本章新增，可为空（策略库覆盖不到时走原有生成逻辑）
    skill,               # 本章新增
    chapter_task,         # 现有细纲 + 第5章 chapter_function
    context               # 现有7层上下文装配（含第4章 Arc摘要）
) -> final_prompt
```

**关键原则**：策略库覆盖不到的场景必须能**优雅降级**到现有生成逻辑，不能因为策略库没匹配到就阻塞生成。

## 7. Agent 调整（挂载点：现有10 Agent + Workflow节点）

### 7.1 现有约束（不可破坏）

- Agent 间禁止互调，禁自治对话（CI 守卫）
- 所有编排必须经 Producer 产出 WorkflowPlan（数据非控制流）

### 7.2 新增 Agent 及接入方式

| 新增Agent | 职责 | 接入方式 |
|---|---|---|
| Planner Agent | 剧情规划（Arc生成） | Producer 在 WorkflowPlan 中新增 agent 节点调度，不由 Story Architect 直接调用 |
| Scene Director | 场景设计 | **第二阶段再做**（依赖"场景"层是否上马，见4.2） |
| Repair Agent | 分级修复 | 见第8章，作为 branch 节点的返工分支，替代现有"整章重写"的粗粒度返工 |
| Learning Agent | 学习作者风格 | 挂在 Knowledge Hub 下，异步任务，不进主生产流水线（避免拖慢单章生成延迟） |

**关键要求**：新增 Agent 一律通过 Producer 编排进 WorkflowPlan 的节点位置来调度，不允许老 Agent 直接函数调用新 Agent，否则违反 CI 守卫会被拦截。

## 8. Repair Engine（挂载点：Quality Engine 返工机制）

### 8.1 现状问题

现有返工机制是 branch 节点"质量分<阈值→整体重跑≤2轮"，粒度是**整章重写**，成本高、且可能反复触发同类问题。

### 8.2 分级修复设计

```
问题发现（Reviewer七维评分 + 读者体验审核）
    ↓
定位（哪个层级出问题）
    ↓
判断级别 → 选择修复方式：
    文字问题 → 句级修复（局部替换，不重新生成）
    表达问题 → 段落级修复
    场景问题 → 场景级重生成（依赖"场景"层，第一阶段暂不做，先按章处理）
    逻辑问题 → 章节级重生成（=现有整章重写，保留作为兜底）
    剧情问题 → 打回 Planner Agent 重新规划（新增分支，之前没有这条路径）
```

### 8.3 第一阶段落地范围

不实现"场景级"修复（依赖场景层）。先实现三级：**句/段级局部修复 → 章节级重写（复用现有）→ 打回规划（新增）**。Repair Agent 只需要新增"句/段级局部修复"和"打回规划"两种能力，章节级重写复用现有实现。

### 8.4 与版本系统的关系

局部修复（句/段级）产生的版本走现有 VersionedRepository，但**不建议**触发"分支"（现有 AI 重写产生分支非覆盖的规则是给整章/整节点级别设计的）；局部修复建议作为同一版本节点内的增量记录，避免版本树因高频小修复而爆炸式增长。这一点需要和现有版本系统负责人对齐，是本文档中**唯一建议偏离 V3 原文"AI重写一律分支"要求**的地方。

## 9. 人物认知分层（挂载点：实体状态表 FR-C6-03）

### 9.1 现状

实体状态表已有"位置/关系/持有物/**已知信息**"，V3 要求把"已知信息"拆分为认知层级。

### 9.2 字段扩展（非新表）

```
character_state.known_info 拆分为：
├── world_facts          # 世界事实（客观存在，不代表任何人知道）
├── reader_known          # 读者已知（叙事已揭示给读者）
├── protagonist_known      # 主角已知
├── character_known         # 该角色已知
└── character_misunderstood  # 该角色误解的内容（明确记录"错误认知"，防止AI帮角色纠错）
```

- 逐章更新机制复用现有实现，只是更新的字段从一个拆成五个
- Reviewer 新增检测规则：正文中出现"角色使用了未标记为其已知的信息"时标记为 OOC/穿帮问题，并入现有 OOC 检测（FR-C6-07），不新建检测器

## 10. 时间线真实锚点（挂载点：时间线系统 FR-C6-05）

在现有"章内事件抽取入表、跨章矛盾检测"基础上新增字段：

```
timeline_event 新增：
├── real_world_anchor   # 可选，关联真实时间点（如"2010年"）
└── anachronism_check    # 校验规则引用（如"不得出现2010年前不存在的产品"）
```

仅在小说明确设定"现实世界背景"时启用（DNA 的 `commercial_positioning` 中标注平台/题材为"现实向"时自动开启此校验，架空/玄幻类不启用，避免误判）。

## 11. 质量控制层扩展

### 11.1 读者体验审核（并入现有七维评分，不新增独立评分体系）

新增检测维度：是否有期待 / 是否有冲突 / 是否有爽点 / 是否有情绪变化 / 是否值得继续阅读。

实现方式：复用现有 Reviewer 的 LLM 评分调用，扩展 Prompt 中的评分维度定义，输出 Schema 增加对应字段——**不是**新建一个 Agent 或新的调用链路。

### 11.2 Pacing Engine（节奏引擎）

现有节奏检测（FR-C6-07）已存在。V3 要求升级为"曲线可视化"，这是**前端工作为主**：

- 后端：把现有节奏检测的输出（冲突/爽点/信息/情绪/悬念的逐章打分）持久化为可查询的时间序列（关联 chapter_id）
- 前端：三栏工作台的"目录/人物/设定"栏新增一个节奏曲线视图（复用现有图表组件，不新增依赖）

## 12. Author Style Card 强化（挂载点：Knowledge Hub 风格学习）

现有已有"样本→特征提取→style_card→注入生成上下文"。V3 要求增加学习来源：

```
新增学习输入源（不改变现有style_card结构，只扩展提取来源）：
├── 修改记录     # 用户在编辑器中对AI生成内容的编辑diff（复用现有版本系统的diff能力）
├── 删除内容      # 同上，diff中的删除部分
├── 保留内容      # diff中未改动部分
└── 喜欢表达      # 用户主动标记的偏好表达（需要编辑器新增"标记喜欢"交互，UI改动）
```

由 Learning Agent（第7章新增）异步消费编辑器 diff 数据更新 style_card，不阻塞实时编辑体验。

按 V3 原文"给AI开发团队的核心要求"，结合本文档的落点分析，正式约定如下提交格式：

```
需求：<一句话描述>

- Agent/节点：<具体到现有哪个Agent或Workflow节点>

影响范围：
- 受影响的现有模块列表
- 是否有向后兼容问题（如旧小说没有Arc/DNA数据时如何降级）

验收标准：
- 真实Provider（非mock）跑通的具体场景
- 对应的自动化测试（纳入现有565+回归套件）

禁止：
- mock数据 / 空页面 / 只建字段不接AI流程 / 假完成
```

## 15. 开放问题（需要你和团队评审，本文档未替你做决定）

1. **场景层是否要做**：V3原文六层规划，本文档建议先做一层（Arc）。如果你判断"信息展示型"章节水字问题主要靠 Chapter Function 就能解决，场景层可以长期不做。
2. **局部修复是否产生版本分支**：第8.4章提出的偏离建议，需要和版本系统设计初衷对齐，避免版本树因高频小修复膨胀。
3. **策略库的维护方式**：是人工持续整理网文套路（成本可控但依赖人力），还是尝试从已完本小说反向抽取策略（技术上是新的研究方向，不建议第一阶段做）。
4. **Learning Agent 的数据来源边界**：编辑器diff涉及用户创作隐私数据，是否需要用户显式同意才能用于风格学习训练，需要和现有协作RBAC/离线策略一起过一遍合规口径。
