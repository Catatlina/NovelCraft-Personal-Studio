# NovelCraft Personal Studio V6/V7 合并报告

## 最新产品决策：不再保留双正文链路（2026-08-02）

本报告原先把 V6/V7 描述为“共享边界、上层并行”的合并候选态。根据真实 DeepSeek 20 章质量证据，本轮已进一步做出产品选型：**V7 是唯一正文生成/连续性/质量审阅/重生成链；V6 只作为兼容事实与产品承载层。**

- 质量依据：V7 20/20、平均 92.0、最低 91.0；V6 20/20、平均 79.6、最低 72.0。
- 产品入口：继续写作、批量生成、自动续写、人工拒绝重生成和 Bootstrap 首章正文均走 V7 Director。
- 兼容边界：V6 保留 `contents`、知识事实、项目映射、编辑器和导出；V7 质量通过后幂等写回同一 V6 章节记录。
- 规划边界：Bootstrap 的规划/蓝图属于结构化创作准备，不构成第二套正文生成链。
- 验收边界：本轮代码收口尚未提交/部署；生产新链路长跑和两位人工盲评仍未完成，不能宣称产品质量已验收。
- 本轮回归：后端 849 passed/138 skipped/1 xpassed/2 warnings；V7 单链路目标组合 46 passed；前端 32 passed，构建通过。

日期：2026-08-02
审计基线：`origin/main` `0a3261d`（2026-08-02 11:01）
目标：判断 V7 是否已经与 V6 完成产品、数据、权限和运行时合并
本轮状态：已在该基线上实现权限桥、V7→V6章节桥、质量合并门、统一 Provider transport、Prompt provenance 和跨版本账本；源码尚未提交/推送/部署。

## 一、合并结论

当前结论是：**V6/V7 已从并行子系统进入“共享 Provider/账本边界、权限与章节桥已接线”的合并候选态；代码级回归可用，但真实数据库/Provider/长跑/人工质量验收仍未完成。**

V7 仍有独立的 API、异步数据库模型、Brain、Director、Trace、成本和 Prompt 模块，但本轮已把 V6 权限依赖、V6 章节事实源和共享 AI 执行边界接入实际路径：通过严格质量门禁的 V7 章节会幂等写入 V6 `contents`，V6/V7 provider 调用都进入 `ai_execution_ledger`；V7 实际调用还会播种/解析 `PromptVersionManager` 并写入 `v7_prompt_executions`。这证明“统一边界已接线”，不等于真实生产数据库已经升级或生成质量已经人工验收。

## 三、逐项合并审计

### 1. 入口层：已接线

`frontend/src/App.tsx:844` 在选择 novel 后渲染 V7 入口，V7 页面可以被打开；最新 Playwright 记录也覆盖了页面 walkthrough。因此“用户能看到 V7”这一点可以标记为**已接线**。

入口传入的是 `novel_id`；后端 V7 路由现在已执行登录态与 novel member/editor 校验，但 V6 project/contents 与 V7 novel 的正式归属映射仍依赖项目上下文，不能仅凭入口可见推断跨域数据已完成统一。

### 2. 数据层：未合并

`backend/app/v7/db.py:5-8` 明确 V7 数据库层与 V6 分离，`v7_001_init_all_tables.py` 初始化独立的 V7 表集合。V7 的 `NovelScopedMixin` 只提供 `novel_id`，没有自动连接 V6 的 project、owner 或 membership。

因此当前是“同一部署环境中的两套数据域”，不是“同一业务实体的统一数据模型”。

### 3. 章节链路：桥接已实现，端到端尚未验收

`backend/app/v7/director/story_director.py` 的 `_update` 现在先构建交接契约；质量门禁通过后调用 `backend/app/v7/integration/v6_bridge.py`，以 `v7:{novel_id}:chapter:{chapter_number}:v1` 幂等写入 V6 `contents`，并在 V7 state 中记录 `v6_content_id`。质量未通过时不写入正式 V6 章节。

当前结果：

```text
V7 生成 → 严格质量门禁 → v7_story_states
                              ║
                              ║  通过后幂等桥接
                              ▼
                 V6 contents → V6 书库 → V6 编辑器/导出
```

代码链路已经闭合到 V6 `contents`，但当前仍不能把“V7 生成成功”解释成“生产环境已验收进入 V6 主产品”：真实 provider、数据库、V6 UI 和导出需补证据。

### 4. 生成质量链路：质量门已接线，真实长篇验收仍是当前缺口

V6/V3 的 `assembler.py` 负责书状态、卷摘要、近章摘要、实体、伏笔和作者风格卡；`chapter_loop.py` 另有结构化审查、连续性守卫和修复原语。V7 则在 `generation_engine.py` 中自建 `ContextAssembler` 与规则式 `DeAIPipeline`，再由独立 `ReviewEngine` 做 7 维评分。

整改前的四个断点已逐项对应到代码路径；当前状态如下：

1. V7 现在保留上一章 1200 字尾部、交接契约、较完整的状态层和 V6 style card，并在上下文超限时优先保留这些锚点。
2. V7 Review 接收上一章尾部与交接契约；V7 章节通过 85 分关键维度门禁后才进入 V6 bridge。
3. V6 连贯性检查失败不再放行；事实 reconcile 支持精确 anchor/replacement，修复后进行二次结构化复核，失败转 `needs_review`。
4. V6/V7 都调用真实 `bootstrap.final_humanize`；Provider 失败、空结果或破坏性缩短不回退成“已处理”。

因此代码层已经把连续性和去 AI 味设为合并门，但只有真实 20 章双轨与人工盲评才能证明用户体验达到目标。具体整改见 [生成质量整改报告_20260802.md](生成质量整改报告_20260802.md)。

### 5. AI 运行时：Provider 传输已统一，上层运行时仍保留适配层

仓库中有以下 V6 adapter：

- `backend/app/v7/adapters/generation_adapter.py`
- `backend/app/v7/adapters/deai_adapter.py`
- `backend/app/v7/adapters/context_adapter.py`

V7 仍由自己的 `AIGateway`、`ContextAssembler` 和 `DeAIPipeline` 负责异步编排；这不是重复 Provider 实现，因为 V6/V7 的 DeepSeek 请求形状、超时、SSE/JSON 响应解析已收敛到 `backend/app/services/unified_gateway.py`。章节数据桥与质量门负责把通过的结果写入 V6 主事实源。

所以该项应标记为：**共享 Provider transport 已接线；V6/V7 的上层 sync/async 编排仍分离，完整产品运行时尚未宣称合并验收**。

### 6. 成本与 Prompt：共享运行时已接线，生产证据待补

本轮新增共享运行时边界：

- `backend/app/services/unified_gateway.py` 统一 V6/V7 DeepSeek 请求形状、超时和响应 usage；V6/V7 只保留各自的 sync/async 调用适配。
- `backend/app/services/ai_runtime.py` 定义统一 `ai_execution_ledger`、精确 rendered prompt hash、执行 key、token/cost/status 和失败字段。
- V6 `app.gateway.complete` 的成功、失败和流式收口写共享账本；同步与流式请求都经过共享 transport，成功写账本失败时不提交成功结果。
- V7 `AIGateway` 在 provider 返回后写 `PromptVersionManager.record_runtime_execution` 和共享账本；Prompt 版本身份由 `ensure_runtime_version` 幂等播种，精确渲染文本/hash 在执行记录中保存。
- `backend/scripts/seed_v7_prompts.py` 提供无模型调用的生产播种命令；`nc_v6_v7_runtime_ledger` 提供正式 migration；Cost API 的 `/ledger` 以认证项目范围汇总 V6/V7，避免 V6 仅有 project_id 时被 novel 过滤掉。

因此该项当前应标记为：**已接线/代码级可用，生产 migration、真实回放和成本对账未验收**。V7 预算门仍由其 novel 预算策略执行，统一账本作为跨版本真实总额来源，避免把 trace 与 prompt execution 重复相加。

### 7. 权限：基础桥已实现，管理面仍需补齐

V7 的 Brain、Director、Trace、Cost 已按 novel scope 接入 `require_novel_member_dep`；读需成员，写需 editor，Director 还会把 project scope 传入章节桥。Prompt 版本表为全局资源，本轮只加了登录态，尚未完成管理员/项目范围的授权模型。

该问题必须在任何跨系统数据桥接之前修复，否则桥接会把 V6 的真实内容暴露给未授权的 V7 请求。

## 六、建议的合并路线

### M1：安全桥的剩余工作

1. 给 Prompt 全局资源补管理员/项目范围权限。
2. 增加双用户真实 API 验收：非成员 403、viewer 禁止写、editor 可写。
3. 将 V6 novel/project/contents 映射做成可查询的正式 provenance，而不只在运行时解析 project_id。

验收：双用户隔离、非成员 403、写操作角色限制、越权审计记录。

### M2：完成章节桥生产验收

V6 `contents` 已作为面向用户的章节事实源，V7 Brain 作为生成上下文与运行状态存储。剩余验收必须通过显式 application service 证明：

1. 现有桥已创建幂等 V6 content，并写入 V6 version；仍需真实验证 version/回滚映射；
2. 保存 V7 run_id、trace_id、prompt_version、cost 作为 provenance；当前已写入 run/评分/去 AI/交接契约摘要，V7 trace/prompt execution 仍需统一；
3. 将章节状态和回滚关系写入统一映射表；
4. 现有桥失败时回滚自身事务，重试不重复创建 V6 内容；仍需补跨域失败补偿；
5. 让 V6 书库、编辑器和导出读取同一事实源。

验收：一条真实 V7 生成结果可在 V6 书库看到、在 V6 编辑器打开、被 V6 导出；回滚后两套状态一致。

### M2.5：把生成质量作为合并门，而不是附加指标

在章节数据桥之前，先统一 `chapter_transition_contract`、事实账本、Review 输入和去 AI 味结果 schema。任一版本生成的章节都必须经过：上一章结尾承接 → 事实/人物/时间线核验 → 局部或整章修复 → 人文化定稿 → 二次核验。连续性检查失败不能放行，Provider 失败不能回退成“已处理”。

最低质量门槛建议：高危跨章事实冲突为 0；连贯性与写作质量逐章不低于 85；20 章长跑末段相对首段下降不超过 2 分；去 AI 味前后剧情事实 100% 不变；并由人工盲评证明整改版优于旧版。

### M3：统一 AI、成本和 Prompt 运行时（代码已接线）

架构决策已落为“共享传输 + 共享执行账本 + sync/async 适配”：V6/V7 不再各自维护 Provider HTTP 形状，包含 V6 流式 SSE；V7 通过 PromptVersionManager 记录运行时版本，V6 通过既有 prompts 版本和共享账本保留 provenance；成本 API 的项目范围查询可同时看到两个版本。所有成功、失败、重试、超预算和人工重试仍需在真实库中回放验证。

### M4：统一前端交互和契约

- GenerationConsole 使用后端正式字段，不再读取不存在的 `step_names`/`run_duration_sec`。
- CostMonitor 与后端 schema 统一，并覆盖空值和异常。
- V7 生成完成后提供“在 V6 编辑器打开”的明确 handoff。
- 删除所有 API 失败时的 demo fallback 和本地伪成功。

### M5：建立合并验收门

至少需要以下证据后，才能把状态改为“可用”，再经过生产回归才能标记“已验收”：

| 验收项 | 必须证明 |
|---|---|
| 权限 | 双用户隔离、非成员拒绝、角色写权限 |
| 数据桥 | V7 → V6 contents → 书库/编辑器/导出完整可见 |
| 幂等/回滚 | 重试不重复、失败不半写、回滚可恢复 |
| AI 真值 | provider、模型、调用、token、cost、trace 可追溯 |
| 预算 | 超预算在 LLM 前阻断，实际成本自动记账 |
| Prompt | active version 与执行记录一致 |
| UI 契约 | Cost/Generation/DecisionLog 真实响应渲染无错误 |
| 生成质量 | 20 章双轨对照、逐章人工盲评、跨章事实和去味差分证据 |
| 质量门禁 | AI development gate、目标单测、全量后端、E2E 均有 commit 绑定记录 |

## 七、最终判定

当前 V6/V7 合并状态：

- 入口和部分页面：**已接线**；
- V7 自身 Brain/Director/Trace 基础能力：**可用（以当前目标测试范围为限）**；
- 共享 Provider/执行账本/Prompt provenance：**已接线/代码级可用，真实数据库回放未验收**；
- 认证、跨域数据、章节落库、编辑器/导出：**部分已接线，真实端到端未验收**；
- V6/V7 全链路产品合并：**不能宣称完成**。

建议下一步直接执行：在真实 Provider 与双项目/双轨数据库环境中运行 20 章脚本，再完成两名编辑盲评；在这些证据完成前，不建议把 V7 生成结果作为“质量已达标”的 V6 正式作品数据对外承诺。本地 migration/播种已经完成，但不能替代真实 Provider 回放、V6 书库/编辑器/导出回写和人工验收。
