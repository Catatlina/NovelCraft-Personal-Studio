# Starlume AI 系统架构与开发文档

> 版本：1.0
> 原则：复用现有单一正文主链，以人工确认和可追溯候选层改造产品，不建设平行生成系统

## 1. 现状与目标

现有系统已经具备 React 编辑器、AI改写预览、真实 Provider 网关、V7故事状态、章节上下文、审阅、连续性、成本和发布准备能力。主要缺口是：

- 产品状态仍围绕自动生成流程组织，人工创作不是第一入口；
- `EditorAiChat` 只在前端保存短期消息并触发单次改写，不是真正的持久化多轮对话；
- 创作圣经分散在内容、知识、V7状态和元数据中，没有统一人工确认界面；
- 多 Provider 已有底层能力，但没有按创作职责编排；
- 没有真实写作会话、建议采用和文本来源区间账本；
- 平台发布准备与平台码字记录尚未形成合法衔接。

目标架构在现有主链上增加“创作控制面”，正式正文仍以 `contents` 为唯一正文真相源。

## 2. 分层架构

```text
┌───────────────────────────────────────────────────────────────┐
│ 体验层：创作圣经｜三栏编辑器｜AI会话｜版本对比｜平台定稿       │
├───────────────────────────────────────────────────────────────┤
│ 应用层：创作会话｜候选管理｜人工确认｜影响分析｜发布编排       │
├───────────────────────────────────────────────────────────────┤
│ AI角色层：总编｜扩写｜对白/读者｜独立审阅｜Provider Router     │
├───────────────────────────────────────────────────────────────┤
│ 确定性治理：权限｜正史优先级｜版本｜哈希｜状态机｜硬事实门禁   │
├───────────────────────────────────────────────────────────────┤
│ 数据层：contents｜创作圣经｜连续性账本｜AI建议｜创作溯源       │
└───────────────────────────────────────────────────────────────┘
```

## 3. 真相源与优先级

系统必须按以下顺序裁决冲突：

1. 作者最新确认的正式设定；
2. 作者确认并保存的正式章节正文；
3. 章节结束后确认的状态快照；
4. 作者确认的分卷/章节/场景计划；
5. AI候选和审阅建议；
6. 模型常识、联网材料和历史缓存。

AI输出不得直接写入 1–4 层。正式写入必须包含 `confirmed_by`、`confirmed_at`、`base_revision_id` 和来源记录。

## 4. 核心状态机

### 4.1 候选内容

```text
generated → presented → partially_accepted / accepted / rejected
                         ↓
                    applied_to_draft → superseded / reverted
```

只有 `applied_to_draft` 会改变编辑草稿；只有作者保存或确认后才改变正式章节。

### 4.2 创作圣经条目

```text
candidate → human_confirmed → active → revised → archived
```

变更 `active` 条目前必须先做影响分析。影响分析失败不阻止作者决定，但必须明确列出未知范围。

### 4.3 章节

沿用现有正文和发布状态，增加作者工作状态：

```text
planning → drafting → author_review → chapter_approved
                              ↓
                     quality_candidate → publish_ready → published
```

AI审阅不能把章节从 `author_review` 自动推进为 `chapter_approved`。

## 5. 建议数据模型

优先扩展现有表；确实无法表达时才新增表。所有新表必须包含项目归属、创建/更新时间和版本字段。

| 数据对象 | 最小字段 | 说明 |
|---|---|---|
| `story_bibles` | novel_id, revision, status, confirmed_by | 作品级正式创作圣经版本 |
| `story_elements` | bible_id, element_type, payload, source | 世界、发动机、读者承诺等可扩展条目 |
| `character_cards` | novel_id, role_level, profile, status | 角色卡与动态晋升状态 |
| `character_relations` | from_id, to_id, state, effective_seq | 有方向、可追溯的关系变化 |
| `plot_lines` | type, objective, state, last_advanced_seq | 主线、支线、感情线等 |
| `outline_nodes` | parent_id, level, payload, revision | 全书、卷、章、场景统一树 |
| `scene_cards` | chapter_id, seq, start_state, intent, result | 当前编辑场景契约 |
| `continuity_facts` | subject, predicate, object, effective_range | 人物、物品、地点和知识事实 |
| `writing_sessions` | chapter_id, started_at, active_ms, device_id | 真实创作会话聚合 |
| `writing_events` | session_id, event_type, delta, revision_id | 批量变化事件，不保存逐键内容 |
| `ai_suggestions` | role, provider, model, prompt, base_revision | AI候选与调用溯源 |
| `suggestion_applications` | suggestion_id, ranges, action, revision | 接受、部分接受、拒绝和撤销 |
| `text_provenance_spans` | revision_id, start, end, origin, confidence | 最终正文来源区间，可重算 |
| `platform_exports` | variant_id, content_hash, exported_at, receipt | 平台定稿包和发布回执 |

文本区间不能只使用易漂移的字符偏移。每次修订后以 diff 重建区间，并保留旧修订的不可变快照和哈希。

## 6. 服务边界

### 6.1 新增应用服务

- `StoryBibleService`：候选、确认、修订和影响分析；
- `CreativeSessionService`：当前章节、场景、角色和故事线上下文；
- `AiCollaborationService`：角色路由、多轮会话、候选和失败语义；
- `SuggestionService`：候选差异、局部采用、撤销和版本关联；
- `WritingLedgerService`：会话、事件、指标和贡献重算；
- `PlatformFinalizationService`：平台规则快照、定稿包和回执。

### 6.2 复用能力

- 复用 `UnifiedGateway`/现有 Gateway 的真实 Provider、预算和 `ai_calls`；
- 复用 V7 `ChapterContext`，将创作圣经和当前场景作为明确组件接入；
- 复用 V7 review、timeline、foreshadowing、state 和 publishing；
- 复用 `Editor.tsx` 的三栏基础和AI预览不覆盖正文不变量；
- 复用版本恢复、离线队列和项目权限。

不得再创建新的 Provider 直连客户端或第二套章节正文表。

## 7. API草案

```text
GET    /api/v1/novels/{id}/creative-context
GET    /api/v1/novels/{id}/story-bible
POST   /api/v1/novels/{id}/story-bible/candidates
POST   /api/v1/story-bible/elements/{id}/confirm
POST   /api/v1/story-bible/elements/{id}/impact-analysis

GET    /api/v1/chapters/{id}/scene-context
POST   /api/v1/chapters/{id}/ai-conversations
POST   /api/v1/ai-conversations/{id}/messages
POST   /api/v1/ai-suggestions/{id}/apply
POST   /api/v1/ai-suggestions/{id}/reject
POST   /api/v1/ai-suggestions/{id}/revert

POST   /api/v1/chapters/{id}/writing-sessions
POST   /api/v1/writing-sessions/{id}/events:batch
POST   /api/v1/writing-sessions/{id}/close
GET    /api/v1/chapters/{id}/writing-report

POST   /api/v1/publication-variants/{id}/finalization-package
POST   /api/v1/publication-variants/{id}/receipts
```

所有写接口必须校验项目归属、`base_revision_id` 和幂等键。版本冲突返回 `409` 和可合并差异，不覆盖新正文。

## 8. AI角色协议

每次请求必须包含：

- `role_key`：chief_editor / scene_expander / dialogue_partner / reader_simulator / critic；
- `task_contract`：目标、范围、不可修改事实、输出结构；
- `context_manifest`：使用了哪些正式事实和版本；
- `base_revision_id` 与选区哈希；
- `provider_route_id`、预算和超时；
- `candidate_only=true`。

响应必须记录 Provider、模型、Prompt版本、上下文清单、token、费用、耗时、原始状态和候选哈希。非法输出、截断、账本写入失败均视为失败。

## 9. 编辑器同步

- 可见 `.ProseMirror` 正文继续同步到即时 ref，保存时以显式文本覆盖异步状态；
- AI请求绑定发起时的 `base_revision_id` 和选区哈希；
- 返回时正文已变化则标记 `stale`，只允许打开差异，不能直接应用；
- AI会话存后端，前端只保存正在输入的临时文本；
- 自动保存正文和批量写作事件使用不同队列，账本失败不得阻断本地正文保存，但必须显示“记录未同步”；
- 离线恢复后按修订和幂等键重放，不能重复计算字数。

## 10. 确定性规则与AI边界

程序规则负责可验证事实：权限、版本、状态转换、哈希、字数、时间、角色位置、物品归属、明确的知识范围、章节顺序、平台规则版本和发布阻断。

AI负责开放语义：多个剧情方向、扩写、对白、角色动机解释、读者感受和有证据的质量建议。

确定性规则不能用关键词密度冒充“爽感”“人味”或第三方检测分；AI也不能改写确定性事实来让结果通过。

## 11. 可靠性与安全

- 真实 Provider 失败直接失败，不返回固定模板、静默空结果或伪降级成功；
- 候选写入与 `ai_calls`/V7 provenance 在同一可恢复事务边界；
- 创作圣经、正文和版本每日备份，迁移前单独备份；
- API Key、平台凭据和用户正文不进入日志；
- 对话上下文按项目隔离，缓存键包含用户、项目、小说和修订；
- 联网材料只进入灵感卡，必须记录URL、抓取时间、许可边界和去标识摘要。

## 12. 可观测性

至少监控：

- 各AI角色成功率、失败类型、截断率、平均费用和P95延迟；
- 候选展示、部分采用、拒绝、撤销和过期比例；
- 人工编辑、AI净保留和版本回滚；
- 连续性冲突、重复建议和无证据建议；
- 创作事件同步失败、版本冲突和平台导出/回执状态。

任何运营面板都必须能追到实际记录，不用硬编码 `available=true` 表示健康。
