## 1. 接手顺序

1. 确认仓库为 `Catatlina/starlume-ai-studio`，工作目录仍可能保留历史名称；
2. 阅读 `AGENTS.md`；
3. 阅读本目录 README、01、03、04、05、06；
4. 阅读 `docs/AI_HANDOFF.md`、`docs/REQUIREMENTS_TRACEABILITY.md`、`docs/KNOWN_ISSUES.md`；
5. 阅读 `docs/ACCEPTANCE_CRITERIA.md` 和本文件；
6. 执行仓库状态、分支、最近提交和差异检查；
7. 复跑交接中与当前切片相关的门禁；
8. 从 03 号文档第一个未验收里程碑继续。

## 2. 当前架构边界

- 正式正文唯一真相源仍是 `contents`；
- V7是故事治理、状态、审阅、成本和溯源控制面；
- 现有编辑预览必须保留“原文不被AI失败或放弃覆盖”的不变量；
- 新辅助创作能力扩展现有编辑器和Gateway，不另建应用；
- 历史 `NOVELCRAFT_*`、数据库名和迁移标识是兼容标识，不代表对外品牌；
- `docs/NovelCraft-开发文档/` 是历史资料，不再是新需求的权威入口。

## 3. 每批交接记录

每次中断或交付，必须在 Git 中记录：

```text
目标与用户入口：
基线提交/分支：
实际修改文件：
复用能力：
新增能力及原因：
执行命令和原始结果：
真实Provider/平台证据：
未运行门禁和原因：
当前状态：未开始/已接线/可用/已验收
下一条可执行命令：
回滚方式：
```

同时更新 `AI_HANDOFF`、`REQUIREMENTS_TRACEABILITY` 和 `KNOWN_ISSUES`。状态与代码必须在同一提交链中。

## 4. 验收层级

| 层级 | 证据 | 允许结论 |
|---|---|---|
| T0 | 文件、路由、组件存在 | 仅说明已接线的一部分 |
| T1 | 纯逻辑单测 | 局部逻辑正确 |
| T2 | API、数据库、权限、持久化 | 后端切片可用 |
| T3 | Provider/Worker真实失败恢复 | 运行链可用 |
| T4 | 浏览器正式入口闭环 | 用户链可用 |
| T5 | 真实Provider、平台、三章、人工盲评 | 对应能力已验收 |

不同能力需要的最高证据不同。平台发布必须有回执；外部分数必须有报告；模型质量必须有真实样本；不能用一个T5结果替代其他外部能力。

## 5. 发布前清单

- 当前工作树只包含本批授权改动；
- `git diff --check`、真实性扫描和强制门禁通过；
- 相关后端、前端、E2E和真实Provider门禁完成；
- 数据库迁移有备份、升级和恢复证据；
- 没有密钥、正文隐私、临时报告和调试日志；
- README、需求矩阵、已知问题和交接状态一致；
- Git提交已推送，CI结果可追溯；
- 部署版本、迁移head、容器健康和公网入口一致；
- 回滚镜像/提交和数据库恢复点已记录。

## 6. 产品发布验收

新辅助创作主线只有在同一生产版本满足以下条件时才能标记“已验收”：

1. 人工确认最小创作圣经；
2. 编辑器显示真实场景、人物和故事线；
3. 至少一个AI角色完成真实多轮候选、局部应用、拒绝和撤销；
4. 正文变化能拒绝陈旧候选；
5. 创作账本能解释人工、AI、粘贴和净增；
6. Provider失败不覆盖正文；
7. 三章空历史副本连续完成并通过两位人工盲评；
8. 七道发布门禁、披露确认、平台定稿和发布回执闭环；
9. 生产登录态桌面、平板和手机关键路径通过。

## 7. GitHub交接

- 主仓库：`https://github.com/Catatlina/starlume-ai-studio`；
- 已存在的 `Catatlina/starlume-ai` 是另一历史项目，不作为本主线远端；
- 当前开发可以继续使用非默认功能分支；合入 `main` 必须单独审查和授权；
- GitHub改名后更新本地 `origin`、README、入口文档和CI/部署引用；
- GitHub通常保留旧URL重定向，但内部配置仍应迁移到新URL，不能永久依赖重定向。

## 8. 中断恢复

额度、网络或外部平台中断时，先停止扩大范围，保存差异和测试结果，写入下一步。不得为了“看起来完成”跳过真实Provider、E2E或平台回执，也不得清理不确定归属的工作树。
