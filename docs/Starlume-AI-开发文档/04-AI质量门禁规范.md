# Starlume AI AI质量门禁规范

> 版本：1.0
> 核心原则：生成时解决自然、可读、连续；后置审计定位问题，不承担默认全文重写

## 2026-08-20 实施状态补充

辅助创作切片新增的确定性规则只负责权限、版本、事实来源、会话状态、幂等事件、Provider 配置状态和人工回执状态；它不通过模型生成内容，也不把启发式结果冒充朱雀等外部检测。AI 候选必须先进入会话和预览，只有作者主动应用后才可进入 `contents` 正文版本。

## 2026-08-21 `lengdu` 方法融合规则

`lengdu` 的可借鉴部分被实现为现有章节骨架入口的生成协议，不复制其 PolyForm Noncommercial 代码或文档，也不把外部“10篇9篇过朱雀”经验当作本项目结论。

生成期新增四条硬要求：

1. 作者意图和已确认事实先于模型顺滑补全；人物先在当前压力下做受限选择，再让信息出现。
2. 每个新增信息必须改变行动、关系、资源、位置、判断或代价之一；场景节点必须留下可见变化。
3. 读者体验以 `reader_experience_plan` 表达为写作靶点：开场抓手、读者发现、期待变化、章末余波、下一章问题。它不输出检测分数，不代表盲评通过。
4. 每个场景结构化为触发→行动→选择→阻力→代价→结果→可见变化；程序门禁拒绝字段缺失、占位词和重复结果，失败不写入骨架版本。

该切片仍是“AI生成700–1000字骨架、作者人工成稿”，没有新增正文长跑或全文后置重写。独立读者复核和外部检测只作为后续受控实验，不能由 Writer 自评替代。

## 1. 门禁目标

质量门禁保护四件事：

1. 正式事实和作者意图不被AI擅自改变；
2. 生成正文能自然阅读并持续推进剧情；
3. 失败候选不落入正式正文或污染后续上下文；
4. 所有评分、Provider、外部报告和人工判断都有真实来源。

门禁不能为了追求“全绿”把正常文学表达机械消灭，也不能用内部启发式冒充第三方检测结果。

## 2. 分层门禁

### G0 作者意图与正史准备

必须具备：当前作品、章节、作者目标、不可修改事实、正式设定版本和正文基线。

阻断条件：项目归属不符、修订不存在、选区哈希不符、作者目标为空、正史冲突未展示。

### G1 上下文完整性

必须具备与当前任务相关的最小上下文：章首状态、当前场景、出场人物、活跃故事线、上章交接和平台限制。

上下文超预算时按重要性压缩解释性材料；不可变事实、人物当前状态和上章交接不能静默删除。关键上下文无法装配时直接失败。

### G2 计划门禁

场景计划至少说明：谁、在哪里、想做什么、遇到什么阻碍、发生什么变化、以什么结果交给下一场。

计划不要求为每段文字分配单一功能，也不要求所有信息立刻解释。章节总字数是主要约束；场景字数只作节拍提示，除非会挤掉后续场景最低表达空间。

### G3 生成门禁

Writer收到自然叙事任务，不收到“规避AI检测”指令。正文必须：

- 通过行动、对白、物件、感官和结果推进；
- 避免作者替读者总结意义、重复解释和完美信息问答；
- 允许人物遗漏、误解、改口和不完整思考；
- 保持角色知识、位置、物品和关系连续；
- 在本章内兑现至少一个可见变化，并留下自然的后续压力；
- 长短句和段落按现场变化，不做机械随机扰动；
- 不为“人味”添加错别字、脏话、无意义动作或生活细节。

Provider截断、输出为空、正文污染、账本失败或硬事实冲突时阻断。最多一次有明确原因的重试；第二次仍失败直接返回失败。

### G4 候选回归门禁

- AI候选只作用于发起时的正文修订；
- 正文已变化时候选标记过期；
- 局部采用不能修改选区外文字；
- 新候选不得降低已确认事实一致性；
- 低风险正文默认冻结，不因另一条建议全文重采样；
- 多候选必须在信息组织方式上独立，不只是换同义词。

程序可以比较确定性回归；语义优劣由作者或独立审阅角色判断，不能由Writer自我宣布通过。

### G5 人工确认门禁

以下动作必须由作者完成：

- 候选应用到草稿；
- 设定进入正式创作圣经；
- 章节从作者审阅进入确认；
- AI披露文案确认；
- 平台定稿和正式发布。

界面必须展示原文、候选、差异、来源模型和影响范围。

### G6 章节质量门禁

复用现有发布准备七道门禁：内容质量、连续性、爽点/兑现、可读性、平台合规、AI披露、外部风险。增加作者侧证据：

- 本章目标是否完成；
- 角色是否保持独立声音；
- 因果是否完整但不过度解释；
- 下一章是否存在真实压力；
- 人工确认和版本记录是否存在。

确定性失败可以阻断；AI低置信度评价必须显示“待人工判断”，不能自动改写正文。

### G7 外部检测与校准

“人工特征95%以上、疑似AI低于5%、AI特征0%”是实验目标，不是内部可推导事实。记录必须包含：

- 实际送检正文哈希和字符数；
- 检测器名称、页面/API、模型版本或更新时间；
- 完整报告或截图；
- 人工、疑似AI、AI三个真实值；
- 送检日期、分段方式和是否与发布正文一致。

没有真实报告时状态只能是“未开始”或“已接线”，不得用关键词、困惑度、模型自评或内部风险分替代。检测结果不免除平台披露义务，也不应用于欺骗平台。

### G8 三章连续验收

前置条件：隔离副本无历史章节和V7故事状态，单章已通过。

三章必须逐章保存：上下文清单、Provider、正文哈希、作者修改、章末状态、七道门禁和人工盲评。任一章阻断即停止；先形成根因假设和最小修复，不连续重复调用Provider。

人工验收至少两人独立评分：可读性、剧情推进、连续性、人物稳定、情绪/爽点、章末继续阅读意愿。自动分数不能替代人工盲评。

### G9 发布门禁

要求平台政策为有效版本、章节与定稿包哈希一致、披露已人工确认、所有阻断门禁通过、发布动作为人工确认或官方API、回执已保存。

没有真实平台回执，只能标记“可用”，不能标记发布“已验收”。

## 3. 生成优先策略

发生质量问题时按以下顺序处理：

1. 检查输入事实和场景目标是否矛盾；
2. 检查上下文是否过多、缺失或优先级错误；
3. 检查角色任务是否交给了错误模型；
4. 修改生成契约或场景组织；
5. 用同一输入做一次受控复验；
6. 仅对明确高风险片段做局部候选；
7. 后置审计重写只作最后兜底。

不得以“继续重试”替代根因分析。

### 3.1 开场分类校准记录（2026-08-20）

开场门禁不应把正常的“短环境落笔，随后立即发生动作”机械判为失败。当前规则保留首句直入动作的优先要求，但对以下有限情况放行：首句分类为 `unknown`、前 160 字内已出现可见动作、且不是身体感受模板。动作出现过晚、全段仍为静态环境、开场重复或身体疼痛模板继续 fail-closed。该规则只修正生成期分类，不调用后置全文重写，也不涉及外部 AI 检测分数。

### 3.2 架空冲突内容策略校准（2026-08-20）

玄幻、悬疑、科幻、历史、游戏和封神等架空题材可以出现服务剧情的非露骨冲突词；系统记录命中并提示作者复核，但不把单个“杀人”等词直接等同于现实违法或露骨暴力。政治、色情、毒品、赌博、自残、现实违法指令和血腥/极端暴力仍为硬阻断；项目可显式关闭 `allow_fictional_violence`。这只是题材语境校准，不是安全规则绕过。

### 3.3 场景预算校准（2026-08-20）

章节总预算是唯一读者硬上限；后续场景最低表达空间用于防止前场吃光章节，不允许把场景目标或读者目标再变成第二个硬上限。场景目标超出时只记录 `scene_reader_budget_variance` 低优先级告警，并继续由章节总预算、完整事件和可读性门禁判断。

### 3.4 最后完整场景自然波动（2026-08-20）

当最后一个场景已经完整完成、没有后续场景需要保留最低表达空间时，允许最多 480 字的有界自然波动，用于容纳结果后的即时后果和章末钩子。该额度不改变读者推荐区间，不允许补写、续写或接近平台级上限；有后续场景、候选不完整或其他质量门禁失败时仍然阻断。

### 3.5 早期爽点 floor 必须在正文前执行（2026-08-20）

前3章的 `early_min_payoff_intensity` 是生成契约，不是正文完成后的评分标签。场景计划若显式声明的爽点强度低于当前 profile floor，必须在正文 Provider 调用前进行一次真实 Provider 计划修复；修复对象是“可见结果→主角主动选择→外部反馈→余波/新压力”的 beats 和契约，不是把 `high` 字段改成 `peak`。修复只能使用当前计划已有事实，确定性复验要求契约字段、五阶段、可见反馈和最低强度全部通过；Provider 表示无法修复或修复后仍不足时，正文生成前直接阻断。该规则已在 `SCENE_SERIAL_GENERATION_VERSION=2.30.0` 本地接线，尚未完成生产复验。

### 3.6 短场景段首重复的专用生成重排（2026-08-20）

短场景不足章节级 12 段样本时，仍保留强重复保护：候选达到 8 段以上、同一姓名至少 4 段且占比至少 45% 时，生成期必须重写。若通用重写未收敛，下一次重写使用专用段落组织指令，要求从动作、物件、声音、环境后果、对白或他人反应起笔；禁止连续同姓名段首、超过四分之一段首、删段、合并段落、只换代词或改写事实。该规则不放宽检测阈值，`2.31.0` 已本地接线，尚未完成生产复验。

## 4. Provider比较

模型比较必须使用同一正式事实、同一任务契约、相近预算和独立空白候选。记录质量、人工采用率、失败率、延迟和真实成本。

不同模型建议并列显示；只有作者选择后才进入草稿。生产未配置真实Key的模型不得参与验收结论。

## 5. 门禁证据

每次门禁记录至少包含：

```text
gate_key, gate_version, input_revision, input_hash,
status, blocking, evidence, provider, model,
prompt_version, executed_at, actor, trace_id
```

允许状态仅为 `passed / failed / needs_human / not_run`。`not_run` 不能计入通过率。

## 6. 修改完成定义

门禁代码存在只能标记“已接线”；正式入口能运行并有本地集成测试可标记“可用”；同一版本经过真实Provider、人工盲评、外部报告或平台回执（按门禁性质需要）后才能标记“已验收”。
