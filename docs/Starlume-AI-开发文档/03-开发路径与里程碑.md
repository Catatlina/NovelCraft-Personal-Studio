# Starlume AI 开发路径与里程碑

> 版本：1.0
> 执行方式：Vibe Coding 小步闭环
> 总原则：先复用、后扩展；先打通一个真实用户结果，再增加第二个对象或模型

## 1. 最小化开发约束

每个开发项开始前必须回答：

1. 现有前端入口能否扩展？
2. 现有 API/service/表能否增加字段或关联表达？
3. V7状态、`contents.meta`、现有版本和 `ai_calls` 能否复用？
4. 新增模块是否会形成第二套正文、Provider或状态真相源？
5. 删除本项后，当前阶段的用户闭环是否仍能完成？

只有前四项证明现有能力不足、第五项证明当前必须时，才允许新增表、服务或页面。不得一次性创建 02 号架构文档中的全部建议对象。

## 2. 当前基线

| 能力 | 当前状态 | 本路线处理 |
|---|---|---|
| 正文编辑、保存、版本恢复 | 可用 | 直接复用，不重写编辑器内核 |
| AI选区/整章候选与预览 | 可用 | 扩展会话和上下文，不新建改写链 |
| 实时审阅、连续性、时间线 | 可用 | 转为编辑侧证据，不另做审阅系统 |
| 多Provider网关、成本和溯源 | 可用 | 增加角色路由配置，不直连新SDK |
| V7 ChapterContext、故事状态 | 可用 | 增加作者确认来源，不复制状态表 |
| 发布准备、披露和七道门禁 | 可用 | 增加人工定稿和创作记录入口 |
| 统一创作圣经 | 已接线 | 先用现有内容/知识/状态聚合验证，再决定最小迁移 |
| 真正多轮AI编辑会话 | 未开始 | 在现有 `EditorAiChat` 上纵向打通一个角色 |
| 写作会话与贡献账本 | 未开始 | 先做章节级聚合和事件表，不做逐键系统 |

状态只表示当前代码事实，不代表新产品方向已经验收。

## 3. 里程碑

### M0：品牌与契约收口

目标：GitHub、README、Agent规则、PRD、架构、门禁和交接统一为 Starlume AI。

最小改动：

- 新建本目录权威文档；
- 现有入口文档改为引用本目录；
- GitHub主仓库改为 `starlume-ai-studio`；
- 保留旧环境变量、数据库、迁移和历史目录兼容名。

验收：链接可达、文档门禁通过、提交推送完成、GitHub新旧URL验证。

### M1：编辑器单角色真实会话

目标：在现有右侧AI会话中跑通一次真实、持久化、可追溯的“作者提问 → AI候选 → 局部采用 → 版本恢复”。

最小切片：

1. 复用 `EditorAiChat.tsx` 和现有 editor op；
2. 复用 `ai_calls`、版本和编辑预览；
3. 只新增会话/消息最小持久化，或先验证能否放入现有运行记录；
4. 首批只启用 `scene_expander` 一个角色；
5. 返回实际 Provider、上下文来源和 `base_revision_id`；
6. 正文变化后旧候选不可直接应用。

门禁：权限、跨作品隔离、Provider失败、陈旧候选、部分采用、拒绝、撤销、刷新恢复和浏览器E2E。

完成前不得同时开发三个模型角色。

### M2：最小创作上下文

目标：作者在编辑器中看见“本章要写什么、谁在场、哪些事实不能错”。

最小切片：

- 先聚合现有 `ChapterContext`、章节细纲、人物和状态；
- 在编辑器右栏增加当前场景卡和人物卡；
- 只允许作者确认或修订关键事实；
- 事实来源可跳转到章节/设定记录；
- 暂不建设完整世界观管理后台。

门禁：上下文与当前小说/章节一致；缺失明确显示；AI回答引用实际来源；确认行为有版本。

### M3：创作圣经最小闭环

目标：一句灵感经AI候选和人工确认形成可用于章节创作的最小创作圣经。

第一版仅包含：

- 作品定位与读者承诺；
- 故事发动机与金手指限制；
- 主角、核心反派、首卷关键配角；
- 主线、首卷阶段目标和第一章计划；
- 不可修改事实和禁写边界。

优先存入现有小说元数据、知识条目和V7状态；只有版本、确认和查询性能无法满足时才新增 `story_bibles`/`story_elements`。

门禁：AI只能生成候选；人工确认前不进入正文上下文；修订可影响分析和回滚。

### M4：多AI角色路由

目标：复用同一 Gateway，为不同任务配置默认模型并显示分歧。

实施顺序：

1. 角色协议和后台路由；
2. GPT总编候选；
3. DeepSeek扩写/结构整理；
4. 豆包对白/读者反馈；
5. 同任务A/B只在人工主动请求时运行。

生产没有对应Key时状态最高为“已接线”。不得用 DeepSeek 假冒豆包/GPT 的真实验收。

### M5：真实码字账本

目标：记录真实人工和AI协作，不记录敏感逐键内容，不模拟平台输入。

最小切片：

- 一张写作会话表；
- 一张批量写作事件表；
- 复用现有版本快照计算差异；
- 先支持人工新增/删除、粘贴、AI采用/撤销、有效时长和净字数；
- 章节报告和CSV/JSON导出。

文本来源区间只有在聚合指标无法解释最终版本时才新增，不作为第一批前置条件。

### M6：平台定稿模式

目标：复用现有发布准备页和 publication variant，生成合法定稿包并保留人工最终确认。

- 番茄作为第一个平台适配器；
- 没有官方API时只做格式化导出和人工回执登记；
- 平台要求在站内完成创作活动时，作者在官方编辑器完成真实最终修订；
- 不做自动键盘回放和伪造时长。

### M7：三章真实验收

目标：替代当前阶段二十章长跑，用更便宜、更可诊断的方式验证产品。

顺序固定：

1. 创建 `active_chapters=0`、无V7故事状态的隔离副本；
2. 单章通过生成/共创、人工确认和质量门禁；
3. 再连续完成三章；
4. 两位独立人工盲评可读性、连续性、角色、爽点和章末吸引力；
5. 第三方检测只记录真实报告，不作为唯一质量裁决；
6. 三章失败后先定位单一根因，不连续盲跑。

### M8：发布闭环与上线

目标：在同一版本上完成披露确认、七道门禁、平台定稿、人工发布和回执。

达到 M8 前不能宣称新的辅助创作主线已验收。

## 4. 当前执行顺序

```text
M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8
```

M1–M3允许在同一设计下复用数据，但验收必须逐个完成。M4以前不并行接入多个新模型；M7以前不恢复二十章长跑。

## 5. 每个切片的Vibe Coding契约

每个切片必须留下：

- 用户入口与期望结果；
- 复用清单和新增清单；
- 输入、输出、状态、不变量和失败语义；
- 最小代码差异；
- 成功、失败、权限、持久化和冲突测试；
- 真实 Provider 或真实平台证据边界；
- 差异审查、回滚点和交接记录。

如果实现范围明显超过本里程碑，应拆分而不是一次性落地完整目标架构。
