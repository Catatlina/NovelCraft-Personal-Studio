## 1. 实施原则

- 不重写现有 React 应用、编辑器、Gateway、V7和发布准备层；
- 不先做“大一统数据模型”，先用现有数据完成一个真实闭环；
- 每批最多增加一个用户结果和它必要的数据；
- AI能力用真实 Provider，失败直接报错；
- 所有候选先预览，所有正史写入必须人工确认；
- 数据迁移只做可回滚的增量，不改历史迁移；
- 页面设计统一到 Starlume AI，不复制字节跳动组件，但参考其清晰层级、克制色彩、留白和高信息效率。

## 2. 第一批：编辑器真实AI共创闭环

### 2.1 复用

| 现有能力 | 复用方式 |
|---|---|
| `frontend/src/components/Editor.tsx` | 保留三栏布局和章节导航 |
| `frontend/src/components/EditorAiChat.tsx` | 从本地确认消息扩展为真实会话视图 |
| `frontend/src/components/RichEditor.tsx` | 保留可见正文同步、选区和保存不变量 |
| `frontend/src/App.tsx` | 先复用现有 editor op 和预览/应用/放弃流程 |
| `backend/app/v7/editor_service.py` | 复用正文事实保护、Provider调用和编辑溯源 |
| `backend/app/services/unified_gateway.py` | 复用Provider、路由、错误、成本和Prompt体系 |
| 现有版本记录 | 关联候选应用和撤销，不新建正文版本表 |

### 2.2 最小新增

只有现有运行记录无法恢复多轮会话时，新增：

- `ai_conversations`：chapter_id、role_key、base_revision_id、status；
- `ai_conversation_messages`：conversation_id、role、content、ai_call_id、context_manifest；
- 候选继续使用现有 pending edit/版本能力；局部采用无法表达时，再为现有版本元数据增加 application ranges。

第一批不新增完整创作圣经表、不接三个新Provider、不做文本来源区间表。

### 2.3 后端接口

优先把现有 editor op 扩展为会话请求；若职责混乱再增加最小接口：

```text
POST /api/v1/contents/{chapter_id}/ai-conversations
POST /api/v1/ai-conversations/{conversation_id}/messages
GET  /api/v1/contents/{chapter_id}/ai-conversations/current
```

消息响应返回 `candidate_text` 或现有编辑预览结构、`ai_call_id`、Provider/模型、上下文清单、`base_revision_id` 和选区哈希。

### 2.4 前端交互

- 会话消息来自后端，不再先插入“收到”冒充模型答复；
- 生成中显示真实请求状态；失败显示Provider错误和重试入口；
- 候选在现有预览区对比，不把长正文塞进聊天气泡；
- 支持整段接受、局部接受、拒绝和撤销；
- 正文修订不一致时显示“正文已变化，请重新生成或仅查看差异”。

## 3. 第二批：当前场景与人物上下文

先增加一个聚合读取接口，不先迁移数据：

```text
GET /api/v1/contents/{chapter_id}/creative-context
```

服务聚合现有小说元数据、V7 `ChapterContext`、当前/上章正文元数据、人物、时间线、伏笔和审阅证据，返回：

- current_scene；
- cast；
- active_plot_lines；
- fixed_facts；
- due_foreshadowings；
- previous_handoff；
- source_manifest。

前端右栏增加“场景 / 人物 / 故事线”三个折叠区。数据缺失显示缺失来源，不让AI自动补成正史。

## 4. 第三批：最小创作圣经

先检查 `contents.meta`、知识条目、V7状态和现有 planning 输出能否表达最小圣经。满足版本与确认需求时，第一版只新增统一读取/确认服务；不满足时增加一张版本表和一张条目表。

确认接口必须支持：

- 单条确认，不要求整份一次接受；
- `base_revision_id` 防覆盖；
- 变更前影响预览；
- 历史版本和恢复；
- AI候选来源。

## 5. 第四批：多AI路由

在现有模型路由中增加 `role_key`，不在代码中写死模型：

```text
chief_editor       → configurable GPT route
scene_expander     → configurable DeepSeek route
dialogue_partner   → configurable Doubao route
reader_simulator   → configurable Doubao/GPT route
critic             → independent configured route
```

没有真实Key时界面显示“未配置”，不自动借用另一个角色模型冒充验收。只有同一任务需要对照时才并发A/B，默认单模型调用控制成本。

## 6. 第五批：创作账本与平台定稿

### 6.1 账本最小数据

- `writing_sessions`：一章一次前台创作会话；
- `writing_events`：每10–30秒批量提交的字数和动作汇总；
- 正文版本继续使用现有版本表；
- AI采用事件关联 `ai_call_id` 和版本。

第一版不记录逐键内容、不做全局键盘监听、不保存剪贴板正文。

### 6.2 平台复用

扩展现有 `PublishingPreparation`、publication variant 和AI disclosure：

- 增加“创作记录摘要”；
- 增加“生成平台定稿包”；
- 增加人工回执登记；
- 平台规则快照过期时继续阻断；
- 不开发模拟键盘或未授权浏览器注入。

## 7. UI与设计系统

### 7.1 视觉方向

- 浅色主题使用暖白/中性灰背景和白色内容面；避免当前浅色页面出现大面积深色卡片；
- 主色使用克制的星光靛蓝，强调色只用于关键动作和状态；
- 8px基础间距，卡片圆角10–12px，边框优先于重阴影；
- 标题、正文、辅助信息形成清楚的三级层次；
- 主按钮每个视图最多一个，危险动作必须二次确认；
- 空态直接告诉作者下一步，不显示虚假统计；
- 右侧AI区像协作侧栏，不像监控后台。

### 7.2 编辑器布局

```text
桌面 ≥ 1280px：260px 导航｜自适应正文｜340px 协作侧栏
平板 768–1279px：导航抽屉｜正文｜可收起协作侧栏
手机 < 768px：正文优先，导航与AI使用底部抽屉
```

正文可读宽度保持约 680–760px；AI建议、审阅指标和上下文不能压缩正文到不可阅读。

### 7.3 可访问性

- 正文和普通文字对比度至少满足 WCAG AA；
- 键盘可以打开上下文、发送消息、接受/拒绝候选和撤销；
- 流式状态、失败和应用成功使用 `aria-live`；
- 不只用颜色表达门禁和版本冲突。

## 8. 测试方案

每批从低到高运行：

1. Schema、格式、类型和 `git diff --check`；
2. 服务单元测试：版本、权限、状态、diff、幂等和失败；
3. API + PostgreSQL集成：项目隔离、持久化、冲突；
4. 前端组件：加载、空态、失败、候选、撤销；
5. 浏览器E2E：真实正文保存、真实AI候选、刷新和恢复；
6. 真实Provider：至少成功一次、失败一次、截断/非法输出一次；
7. 三章隔离副本和人工盲评；
8. 生产健康、登录态、关键链路和回滚验证。

全量测试受环境阻断时不能宣称全量通过。

## 9. 发布与回滚

- 所有新入口先使用功能开关，仅对测试作品开启；
- 迁移前备份数据库并验证压缩包；
- 新表和新字段先兼容旧代码，稳定后才切换默认入口；
- 回滚优先关闭功能开关和回退应用镜像，不删除新数据；
- 正文和创作圣经迁移必须可逆，禁止原地批量覆盖；
- 每批部署后执行生产登录态 smoke，外部Provider只做一次有明确目标的受控验证。

## 10. 交付边界

本方案是实施契约，不代表这些功能已经存在。第一批完成前，多AI实时对话、统一创作圣经、码字账本和平台定稿仍分别标记“未开始”或“已接线”，以需求追踪矩阵为准。
# 2026-08-21 实施补充：作者主导章节骨架

本阶段采用最小垂直切片，不重建正文、Provider或版本系统：

1. 复用 `authoring` 路由和 `gateway.complete()`，新增 `chapter_skeleton` 输出契约与 `authoring.chapter_skeleton` Prompt。
2. 复用 `versions` 保存骨架，不写入 `contents.body`；AI生成和人工修改分别保存不同版本。
3. 复用当前作品的 Bible、V7 story state、故事线和伏笔作为上下文来源；没有事实时明确显示“待人工确认”。
4. 编辑器用单一章节骨架面板承载“输入灵感→生成→人工修改→保存”；正文编辑器只承担人工写作和选区级候选。
5. 只有本地契约/构建通过后，才进行一次生产真实 Provider 骨架样本；失败直接记录 Provider/契约错误，不循环试错。

实施结果补充（2026-08-21）：首轮真实 Provider 样本返回466可见字，按门禁拒绝且未写正文；定位为 Prompt 缺少长度预算后，升级 `authoring.chapter_skeleton` 到 `1.1.0`，增加7个小节预算。修复后生产 DeepSeek 样本813可见字并写入独立骨架版本，正文摘要前后不变。该证据只证明技术链可用，不替代多样本质量、浏览器登录态或长跑验收。

本阶段不做：整章自动写作长跑、后置全文去AI、检测分数驱动生成、自动覆盖原稿或新增并行正文表。
